# Skill Matcher — 任务前置技能匹配与调用

定位一句话：**先想清楚该用哪把工具，再动手。**

## 一、定位与边界

本技能是**元技能 / 路由层**，只做三件事：**扫描 → 匹配 → 调度**（调用或询问）。它不执行任何具体业务任务，也不改变被选中技能的内部流程。

与其他技能的关系：

- **与业务技能**：编排关系，不是竞争关系。命中后立即把执行权交给被选中的技能，后续以该技能的指令为准。
- **与 clarify-before-action 等前置澄清技能**：先后关系。本技能先跑（决定**用什么**），澄清技能后跑（判断需求是否够清晰）。若匹配结果本身需要用户确认，把澄清问题**合并进同一条消息**，不要连开两轮提问。

## 二、触发时机

**主触发**：用户发来一条包含"要做的事"的消息，且尚未开始执行时。

**快速跳过**——满足任一条件即跳过匹配，直接执行原任务：

1. 纯闲聊、寒暄、致谢、情绪表达（"你好" / "谢谢" / "在吗"）
2. 简单事实问答、单点查表、单位/日期换算、翻译一句话——**任务本身不需要任何技能介入**（如"解释一下 CAP 定理"）
3. 用户已点名技能（"用 xx 技能做…"）→ 直接调用该技能，不再匹配
4. 同一任务线的追问或修正，且已有技能正在承担该任务 → 沿用，不重新匹配
5. 本会话中已对同一任务完成过匹配，且结论未变

跳过时**不要声明"已跳过匹配"**，静默直接干活。

> **区分两个易混概念（决定输出长度）**
>
> | 情况 | 含义 | 输出 |
> |---|---|---|
> | **跳过** | 任务本身不需要技能（闲聊、问答、查表） | **静默**，一个字都不说 |
> | **静默执行** | 需要技能，但现有技能相关度不足、调用不划算 | **静默**，不调用、不提 |
> | **未命中** | 任务明显需要专科技能，但没有任何技能对口 | **说一句话**（见 §4.C），然后执行 |
>
> 判据：任务属于"跳过"三类（闲聊 / 常识问答 / 查表）→ 跳过；否则先跑匹配，按 §3 第 3 步判定。


## 三、匹配流程

### 第 1 步：取技能清单

优先使用会话上下文中已注入的可用技能清单（含 `name` 与 `description`）。若该清单不可见或明显不完整，回退为读取技能目录：

- 用户级：`~/.workbuddy/skills/*/SKILL.md`
- 项目级：`{workspace}/.workbuddy/skills/*/SKILL.md`
- 插件与内置技能：按其登记的 location 路径

只读 frontmatter 的 `name` 与 `description` 字段，**不要读入全文**。

### 第 2 步：打分

对每个技能按"相关度"归入三档：

| 档位 | 判据 |
|---|---|
| **高** | 技能描述明确覆盖任务的核心动作或产出物类型；调用它会显著提升结果质量或改变执行方式 |
| **中** | 领域相关、方法可借鉴，但并非任务的必经路径；调用与否结果差异有限 |
| **低 / 无关** | 领域不搭，或仅有字面词语重合 |

判定要点：

- 看**任务的实质动作与产出物**，不看关键词字面重合。"生成一份报告"与某个 report-generator 未必相关——要看报告的类型、受众与格式。
- 一个任务最多保留 3 个高/中候选；低档位一律丢弃，不列出。
- 只保留**能说清楚为什么相关**的候选。理由说不出口，就是无关。
- **高/中边界（易争议，按此裁定）**：只有当你确信调用该技能会让**产出物的形态或质量规格发生实质改变**时，才算"高"。若用户表达的是"大概看看 / 只要个结论 / 随便整理一下"这类**轻量意图**，而技能产出的是重型交付物（文件、站点、长流程），一律**降为中档 → 静默执行**。宁可漏调，不可越权。

### 第 3 步：决策（按顺序判定，命中即停）

**判定顺序不可跳步：**

1. **是否命中快速跳过（§2）？** 是 → 静默执行，结束。不再往下判。
2. **过滤**：丢弃全部低档位候选，只保留高 / 中档。
3. **按剩余候选的数量与性质判定**：

| 剩余候选 | 附加条件 | 动作 | 输出长度 |
|---|---|---|---|
| **0 个**（全部被丢弃） | 任务确实需要专科技能 | **未命中** → 说一句"现有技能里没有对口的，我直接做"，然后执行 | 1 句 |
| **恰好 1 个 · 高** | 该技能**不会**改变执行方式 | **直接调用** | 1 句 |
| **恰好 1 个 · 高** | 该技能**会明显改变**执行方式 | **先确认**，说明会变成什么样 | 确认块 |
| **≥2 个 · 高** | 或高分候选导向明显不同的执行路径 | **先确认**，列候选 | 确认块 |
| **仅中档**（1 个或多个） | — | **静默执行**，不调用、不提 | 0 |
| **0 个**，且任务属于"跳过"三类 | — | **静默执行** | 0 |

**"改变执行方式"的定义**：调用后产出物形态、依赖引入、耗时量级或可逆性，会与用户表述的预期明显不同。典型情形——用户只想要一段答案，而技能会强制产出文件；用户要的是即时结果，而技能会启动长流程；技能会新增外部依赖或产生对外发送行为。

判据不确定时，取**更轻**的动作：能静默就不说，能直调就不问；只有当"猜错会导致返工"时才升级为确认。


## 四、输出规范

### A. 直接调用（唯一高置信度）

> 用 `<skill-name>` 处理：<一句话理由>。

随后立即调用该技能，不再多言。

### B. 需要确认（多候选）

```markdown
这几条路差别不小，先定一下（回字母即可）：

**1. <skill-name>** — <一句话用途>
   匹配理由：<它覆盖了任务的哪个关键动作>
**2. <skill-name>** — <一句话用途>
   匹配理由：<...>
**3. <skill-name>** — <一句话用途>
   匹配理由：<...>

> 也可以直接说"按你的判断"，我选 1 并标出假设。
```

规则：

- 候选 **≤ 3 个**，宁少勿多。
- 每条必须同时带**一句话用途**和**匹配理由**，缺一不可。
- 不出"其它 / 都行 / 看情况"这类占位项。
- 用一句话点明**为什么需要问**（差异在哪：产出物形态、成本、可逆性、耗时）。
- 一条消息只发这一块，不夹带执行动作。**唯一例外**：按 §1 与前置澄清技能的合并规则，需要澄清时必须把澄清问题并入同一条消息，不得连开两轮提问。

### C. 未命中

> 现有技能里没有对口的，我直接做。

然后正常执行。**不解释技能库、不罗列"我检查了 N 个技能"。**

## 五、兜底与克制（硬性约束）

- **不强行调用。** 宁可不用技能，也不要为了用而用。相关度不足时正确的动作是"什么都不说，直接做"。
- **不重复调用。** 同一会话内同一任务已由某技能接管，后续追问沿用，不再触发匹配。仅在**任务线切换**（新话题）时重新匹配。
- **不打断工作流。** 只在"匹配结果会改变执行方式"时才发确认；其余情况一律静默。单轮最多 1 次匹配输出。
- **不表演匹配过程。** 不输出打分表、不输出"正在扫描 N 个技能……"。用户只该看到结论。
- **不越权。** 本技能不替代被选中技能的流程。
- **用户说"别管技能 / 你直接做"** → 立即停止匹配，按原任务执行，本会话内不再主动匹配。

## 六、反模式

| 念头 | 现实 |
|---|---|
| "多列几个候选，显得我考虑周全" | 超过 3 个 = 把选择困难甩给用户。 |
| "这个词技能里有，应该相关" | 字面重合 ≠ 相关。看动作和产出物。 |
| "反正调一下也没坏处" | 不相关的技能会污染上下文、拖慢执行、带偏方向。 |
| "每次都汇报一下匹配结果" | 只有"未命中"才说一句话；跳过与静默执行都是零输出。 |
| "上一轮调过了，再调一次比较稳" | 同一任务线重复调用 = 打断工作流。 |
| "匹配和澄清分两条消息发" | 两轮提问是双重打断。合并成一条。 |

## 七、速查

| 项 | 上限 / 规则 |
|---|---|
| 候选技能数 | 0–3（先丢弃低档，再看剩余） |
| 自动调用条件 | 高置信度 **且** 唯一 **且** 不改变执行方式 |
| 询问条件 | 多个高分候选，或高分候选会明显改变执行方式 |
| 单个候选必带字段 | 名称 + 一句话用途 + 匹配理由 |
| 输出长度 | 三档：确认块（要问）／1 句话（直调、未命中）／0 输出（跳过、静默执行） |
| 单轮确认次数 | 1 |
| 同一任务线重复调用 | 0 |
| 未命中时的输出长度 | 1 句话 |
